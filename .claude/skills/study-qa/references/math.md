# 수학(수학코치) 정합성 매트릭스·체크리스트

> `study-qa` 스킬에서 수학 과목 검증 시 읽는다. 영어는 `english.md`.
> 원문 스펙: `docs/harness/math.md`.

수학은 영어와 검증의 무게중심이 다르다. 영어는 **구조 정합성**(개수·비율·4중 정의)이 중심이었지만, 수학은 **답이 맞는가**가 중심이다. 틀린 답이 통과하는 것이 이 과목의 최악 결함이다.

## 1. 심판 2겹이 실제로 작동하는가

| 검증 | 확인 방법 | 실패 시 의미 |
|---|---|---|
| 호출 C에 B의 답이 안 넘어가는가 | C의 입력 조립 코드를 읽고, 실제 요청 본문을 루프백 스텁으로 캡처 | 심판이 답안지를 봤다 → 검산 무의미 |
| 답 불일치 시 `held`가 되는가 | 스텁으로 B와 C가 다른 답을 주게 만들고 결과 확인 | 틀린 답이 `ok`로 통과 |
| 재시도가 정확히 1회인가 | 계속 불일치하는 스텁으로 호출 수 카운트 | 비용 폭주 |
| `confidence: 'low'` → `held` | 스텁 응답으로 확인 | AI가 자신 없다고 말했는데 무시됨 |
| 재시도 시 C도 새로 부르는가 | 호출 수와 순서 확인 | "두 번 독립 확인"이 성립 안 함 |

**`compare()` 정규화가 과하지 않은지 반례로 확인하라.** 서로 다른 대상(예: `"가"`와 `"나"`)이 같다고 판정되면 심판이 무력해진다. 조사 제거가 의미를 바꾸는 경우를 찾아보라.

## 2. `verifyScene` — 틀린 입력을 실제로 거부하는가

**"규칙이 존재한다"가 아니라 "반례를 거부한다"를 확인한다.** 순수 함수라 무비용으로 전부 테스트 가능하다.

각 규칙마다 통과 케이스 1 + 반례 1을 넣어라. 특히:

- **되감기 등식**(규칙 4): `values[from] = prev[from] + amt`, `values[to] = prev[to] − amt`를 한 칸 틀린 값으로 넣어 거부되는지
- **`start` ↔ `answer` 일치**(규칙 5): 라벨은 맞고 값만 다른 케이스
- **보존량**(규칙 7): 합이 `total`과 1 차이 나는 케이스
- **`values.length` ≠ `entities.length`**(규칙 1): 가장 흔한 AI 실수

실패 사유 문자열이 **어느 단계·어느 인덱스·기대값·실제값**을 담는지도 본다. 재시도 프롬프트에 그대로 실리므로, 사유가 모호하면 재시도가 같은 실수를 반복한다.

## 3. 2단 HTML — 격리가 진짜 되는가

| 검증 | 확인 방법 |
|---|---|
| `sandbox="allow-scripts"`에 `allow-same-origin`이 **없는가** | iframe 속성 문자열 직접 확인. 둘이 함께 있으면 샌드박스가 사실상 해제된다 |
| CSP meta가 `default-src 'none'`인가 | `srcdoc` 조립 결과 확인 |
| 정적 검사 차단 목록이 실제로 걸리는가 | 금지 문자열을 넣은 HTML 샘플로 재생성 유발 확인 |
| 답 태그 대조가 불일치를 잡는가 | `<script id="answer">` 값을 다르게 만든 샘플 |
| 3초 타임아웃 폴백 | `ready`를 안 보내는 샘플로 텍스트 3막 폴백 확인 |
| 라벨 정규화가 `compare()`와 같은 구현인가 | 두 곳이 따로 만들어졌으면 그 자체가 결함 |

**격리가 1차 방어, 정적 검사가 2차라는 순서**가 코드에도 반영됐는지 본다. 정적 검사를 통과했다고 iframe 속성을 느슨하게 하는 코드가 있으면 실패 판정.

## 4. 비용 안전장치

- 판독 확인 화면에서 **설명 만들 문제를 고르게** 하는가 — 페이지 전체를 자동 처리하는 경로가 있으면 문제 6개 × 4회 = 24회가 한 번에 나간다
- 호출 E가 1단 가능 문제로 새지 않는가 — `scene`이 있는데 `sceneHtmlRequest=true`인 케이스를 거부하는가
- E 호출 수·`held` 비율이 로깅되는가 — `{problemPattern, status, attempts}`가 함께 남아야 분석이 된다

## 5. 4중 정의 (영어와 공통)

`프롬프트 ↔ JSON Schema ↔ zod ↔ eval`. 수학에서 물린 값:

| 제약 | 프롬프트 | JSON Schema | zod | eval |
|---|---|---|---|---|
| act2 steps 3~6 | ✔ §3-1 | — | ✔ | ✔ 점검 7 |
| act3 checks 2~3 | ✔ §3-1 | — | ✔ | ✔ 점검 7 |
| rules 2~3 | ✔ §3-1 | — | ✔ | ✔ 점검 7 |
| scene steps 3~8 | ✔ §3-1 | — | ✔ | ✔ 점검 2 |
| `problemPattern` 8종 | ✔ §3-1 | ✔ enum | ✔ | ✔ 점검 3 |
| `scene.kind` 3종 | ✔ §3-1 | ✔ enum | ✔ | ✔ 점검 2 |
| `scene`과 `sceneHtmlRequest` 배타 | ✔ "1단이 우선" | — | ✔ | ✔ 점검 9 |

**JSON Schema에 `minItems`/`maxItems`를 넣지 마라**(strict 제약). 개수는 zod가 본다.

## 6. 경계면 (앱 연결 후)

- `explainProblem()` 반환 `{content, sceneHtml, sceneTier, verify}` ↔ UI 소비 필드
- `held` → "아빠가 한 번 확인해 주세요" 배지 + **답 접힘**이 실제로 되는가
- 판독 확인 화면의 **수정본**이 B의 입력으로 가는가 (원본이 가면 사용자 수정이 무시된다)
- `isWorksheet=false` → 재촬영 안내 + 직접 입력 폴백
