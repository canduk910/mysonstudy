## 건드리지 않는 것 — 정확성 장치

이것들은 품질 다이얼이 아니다. `math-verifier` 영역이다.

- 호출 C(검산) 프롬프트 — 심판이라 표현을 다듬을 이유가 없다
- `verifyScene` 8규칙 — 코드 검산
- `held` 판정 기준 — `confidence: 'low'` → 보류, 답 불일치 → 보류
- 호출 A(문제 판독) "풀지 않는다, 읽기만 한다" 규칙

**`held`가 많다고 다이얼을 풀지 마라.** 보류가 줄어드는 대신 틀린 답이 아이에게 간다. 보류율이 높으면 그건 **그 유형 프롬프트를 손볼 신호**이지 검산을 느슨하게 할 신호가 아니다(`docs/harness/math.md` §8).

## 1단/2단 경계 다이얼

`sceneHtmlRequest`를 언제 켜는지는 비용에 직결된다. 호출 E는 출력 한도 ~8,000이라 문제당 토큰이 크다.

- B 프롬프트의 **'1단 우선'** 규칙을 약화시키지 마라 — 1단으로 되는 문제가 2단으로 새면 비용이 몇 배가 된다.
- E 호출 비율이 오르면 다이얼을 조이는 대신 **그 유형의 전용 렌더러(1단) 추가**를 제안한다. player-builder·math-verifier와 함께 하는 작업이다.

## eval 실행 — 비용

`npm run eval:math`. 픽스처 4문제(1단 2 + 2단 2), 문제당 B+C 2회, 재시도 시 4회 → **최소 8회, 최대 16회**. 2단 픽스처는 호출 E까지 더해진다.

영어(3회)보다 훨씬 비싸다. **오프라인으로 확인할 수 있는 것은 전부 오프라인에서 끝내고 실호출은 마지막 1회.** 무비용 수단:

- `verifyScene`은 순수 함수 → 단위 테스트로 전부 커버 가능
- 정적 검사·답 태그 대조 → 저장된 HTML 샘플로 확인
- 루프백 스텁(`OPENAI_BASE_URL`) → 파이프라인 흐름·재시도·`held` 분기 검증

## 픽스처

`docs/harness/math.md` §7 + 개발 프롬프트 §12의 4문제. 각 픽스처는 `expectedAnswer`·`expectedSceneKind`·`expectedPattern`·`expectedTrap`을 갖는다.

**픽스처 값은 스펙 원본이다. 임의로 바꾸지 마라.** 특히 `expectedAnswer`를 모델 출력에 맞춰 고치는 것은 회귀 테스트를 스스로 무력화하는 짓이다 — 답이 다르면 프롬프트를 의심하지 픽스처를 의심하지 않는다.

채점 픽스처(점검 5)는 의도적으로 `childAnswer`를 넣어 `correct`/`partial`을 확인한다. 이 값을 지우면 채점 경로가 통째로 미검증이 된다.

## eval이 못 잡는 것

- **그림이 실제로 말이 되는지** — `verifyScene`은 숫자만 본다. 장면이 아이에게 이해되는지는 사람이 본다.
- **2단 HTML의 시각적 품질** — 정적 검사·답 대조는 통과해도 화면이 어색할 수 있다. headless `ready` 수신은 "죽지 않았다"까지만 보증한다.
- **비유의 다양성** — "매번 같은 비유를 쓰지 말라"는 규칙은 한 번의 eval로 검증되지 않는다. 여러 문제의 산출물을 모아 봐야 한다.

이런 것은 리포트에 **미검증으로 정직하게 남긴다.**
