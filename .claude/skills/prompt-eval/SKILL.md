# Prompt Eval — 프롬프트 튜닝과 회귀 평가 (과목 공통)

프롬프트도 코드처럼 다룬다: **수정 → eval → 통과 → 커밋.** 학습자의 반응이 유일한 진짜 지표이고, eval은 회귀를 막는 안전망이다.

## 어느 references를 읽을 것인가

작업 과목의 파일 **하나만** 읽는다. 여러 개를 읽으면 컨텍스트만 늘고 다이얼 이름이 섞인다.

| 과목 | references | 다이얼 예 |
|---|---|---|
| 영어 (북카드·단어장·챕터 리더) | `references/english-dials.md` | 단어 개수, challenge 비율, 질문 유형, hintKo 밀도, 줄거리 분량, 영영 정의, 단어 뜻 길이, 유의어 후보 |
| 수학 (수학코치) | `references/math-dials.md` | 비유 종류, act2 단계 수, 규칙 카드 개수, 연습문제 숫자 범위 |
| 일본어 (아빠의 일본어) | `references/japanese-dials.md` | 예문 길이, 대화 해설 항목 개수(goods·fixes·items·practice), 한자 읽기 개수. 레벨당 단어 개수(10)는 다이얼이 아니라 사용자 확정값이다(`japanese.md` §0-2) |
| 토익 (아빠의 영어 · 토익스피킹) | `references/toeic-dials.md` | 발화 포인트 useIn 개수·문장 길이, 모의고사 지문 단어 수·파트별 모범답변 길이·목표 등급별 수준, 피드백 fixes 개수. 목표 등급(IM3·IH·AL)은 다이얼이 아니라 사용자가 모의고사를 만들 때 고르는 값이다 |

## 튜닝 루프

1. 피드백 원문을 다이얼로 번역한다 — "너무 어려워"는 다이얼이 아니다. 어느 숫자를 어느 방향으로 얼마나 움직일지로 옮긴다.
2. 다이얼과 물린 **모든 지점을 한 번에** 바꾼다(아래 4중 정의 + 스펙 코드블록).
3. `EVAL_OFFLINE_ONLY=1`로 해당 과목 eval을 돌려 정의 동기화와 spec-sync를 확인한다(실호출 0).
4. 실호출 검증이 필요하면 무엇을 몇 회 돌릴지 리포트에 적는다. 동의를 받은 오케스트레이터가 실행한다.
5. 통과했을 때만 커밋을 권고한다.

## 눈높이는 과목마다 반대다

같은 "어려워"가 과목마다 다른 다이얼이다.

- **영어·수학 — 은우(초등학생).** 프롬프트에 "쉬운 말·초등 눈높이"가 박혀 있다. 어렵다는 피드백은 어휘·문장 길이를 낮추는 쪽으로 옮긴다.
- **일본어 — 아빠(성인 학습자).** JLPT 등급이 요구하는 어휘·문법을 그 수준 그대로 쓴다(`docs/harness/japanese.md` §0-1). 쉽게 풀어 쓰느라 등급을 낮추면 학습 목적이 깨진다. "어려워"는 **레벨을 낮추는 다이얼이 아니다** — 레벨은 사용자가 화면에서 고른다. 다이얼로 옮길 수 있는 것은 해설의 친절함(`whyKo`·`usageKo`의 깊이)과 예문 길이다. 주제와 레벨이 부딪히면 레벨이 이긴다(§2-0).
- **토익 — 아빠(성인 토익스피킹 수험자).** 은우와 언어는 같지만 눈높이는 일본어 쪽이다(`docs/harness/toeic.md` §0-1). 모범답변은 사용자가 고른 목표 등급(IM3·IH·AL)의 수준 그대로 쓴다. "어려워"는 먼저 등급 선택을 확인하고, 다이얼로는 폭 안의 길이와 설명의 실용성만 움직인다.

영어 튜닝에서 효과를 본 관용구("예시를 더 쉬운 단어로")를 일본어·토익으로 옮겨 오지 마라. 반대 방향으로 작동한다.

## 4중 정의 — 이 프로젝트의 핵심 제약

같은 값이 **프롬프트 ↔ JSON Schema ↔ zod ↔ eval** 네 곳에 각각 있다. 한 곳만 고치면 런타임 검증과 eval이 어긋나고, 그 어긋남은 실호출을 해야 드러난다(비싸다). 여기에 다섯 번째 지점이 있다 — **스펙 문서의 프롬프트 코드블록.** `scripts/spec-sync.ts`가 프롬프트 상수를 스펙 코드블록과 바이트 단위로 대조하므로, 문구를 바꾸면 스펙도 같은 문자열로 바꿔야 오프라인 eval이 통과한다. 일본어·토익 eval은 JSON Schema까지 스펙 코드블록과 의미 동치로 대조하고, 토익은 사용자 메시지 템플릿과 호출 옵션 문장(temperature·maxOutputTokens)까지 스펙과 대조한다.

세 가지를 지켜라:

- **JSON Schema에 `minLength`/`maxLength`/`minItems`를 넣지 마라.** strict 모드 제약이다. 길이·개수 검증은 zod가 담당한다.
- **숫자는 가능하면 프롬프트에 박지 말고 계산해 주입하라.** 프롬프트와 eval이 같은 함수를 부르면 사람이 손으로 맞추던 드리프트가 사라진다. 영어 줄거리 분량은 `buildCardUserMessage`가 `storyOutlineSentenceRange()`로 구간을 계산해 주입하고 eval이 같은 함수로 잰다. 일본어 레벨당 개수는 `buildJaVocabUserMessage`가 `{count}` 자리에 채운다(`planIncludeDistribution`은 모든 레벨에 같은 개수를 주고, 꼭 넣을 단어 `include`는 첫 레벨에만 싣는다). 이 개수(10)는 사용자 확정값이다(`japanese.md` §0-2) — 사용자가 바꾸기로 하면 `JA_VOCAB_DEFAULT_COUNT`와 `JA_ENTRIES_MAX`를 **함께** 올린다(둘은 별도 상수라 하나만 올리면 zod가 초과분을 거부한다. `JA_INCLUDE_MAX`는 기본 개수를 따라간다).
- **zod는 거부선이지 목표가 아니다.** 프롬프트가 겨냥하는 폭과 zod가 허용하는 폭이 다른 다이얼이 있다(일본어 대화 해설: 프롬프트는 items 3~6·practice 2~3을 겨냥하고, zod는 `JA_DIALOG_ITEMS_MIN/MAX`·`JA_DIALOG_PRACTICE_MIN/MAX`로 더 넓게 받는다. 토익 모의고사 C도 `TOEIC_MOCK_ZOD_BANDS`로 넓게 받는다). 반대로 **여유 폭이 없는 다이얼**도 있다 — 토익 발화 포인트 B(`TOEIC_POINTS_LIMITS`)와 피드백 D의 개수는 zod가 프롬프트 숫자와 같아서, 프롬프트만 움직이면 즉시 거부가 난다. 목표를 조이면서 zod까지 같은 폭으로 조이면, 조금 벗어난 출력이 재요청 뒤 throw가 되어 사용자에게는 생성 실패로 보인다. 어느 쪽을 움직였는지 리포트에 적는다.

## 다이얼이 틀렸을 때를 알아채라

같은 항목이 2회 연속 실패하면 프롬프트를 더 조이지 마라. **근거보다 많은 것을 요구하는 다이얼은 모델이 아니라 다이얼이 틀린 것**이다.

실제 사례: 영어에서 "본문 근거가 있으면 줄거리 6~8문장"이라는 평평한 규칙을 걸었더니 모델이 5문장을 냈다. 파보니 픽스처의 장면 근거가 4개뿐이라, 근거보다 많이 쓰라는 요구였다. 모델이 규칙(지어내지 말 것)을 지킨 것이었고, 고칠 곳은 모델이 아니라 다이얼이었다 — 분량을 근거 양에 비례시키자 통과했다.

이런 판단이 서면 실패 사례와 분석을 리포트에 담아 **사용자 논의로 올린다.**

## 정확성 장치는 다이얼이 아니다

품질 다이얼이 아니라 정확성 장치다. 튜닝에서 건드리지 않는다.

| 과목 | 장치 | 왜 건드리면 안 되나 |
|---|---|---|
| 영어 | 판독 프롬프트 — 호출 A(표지)·A′(본문·목차)·C(단어장 원문 전사) | 보이는 것만 옮기는 호출이다. 표현을 다듬으면 창작이 새어 든다 |
| 영어 | grounding 가드 — `groundChapters`·`isGroundedInTranscript`(자막에 없는 en 문장을 저장 전에 잘라낸다), `resolveAllowedStorySource`(넘긴 근거보다 높은 storySource를 zod가 거부) | 프롬프트 지시로 끝내지 않은 "자막 밖 창작 금지"의 최종 강제다. 느슨해지면 지어낸 문장이 원문처럼 저장된다 |
| 수학 | 호출 C(검산)·`verifyScene`·`held` 판정 | 보류가 줄어드는 대신 틀린 답이 아이에게 간다 |
| 일본어 | 호출 B(대화 전사, temperature 0) 프롬프트 | 사진에 있는 것만 옮긴다. 해설은 호출 C가 따로 한다 |
| 일본어 | 토큰 무결성 zod — `surface`를 이으면 원문(`word`·`example.ja`·`definitionJa`)과 정확히 같아야 한다 | 어긋나면 후리가나가 본문을 왜곡한 것이다 |
| 일본어 | `applyVocabPostprocess` — 제외 재적용·포함 우선·kana 기준 중복 접기·레벨 태깅 | 모델이 어겨도 저장에는 안 들어가게 하는 진짜 방어선이다. 레벨은 모델이 아니라 코드가 붙인다 |
| 일본어 | 시험의 모드별 숙련도 분리(`aggregateJaStatsByMode`) | 뜻은 알고 독음을 모르는 상태가 흔하다. 섞이면 "안다"는 판정이 거짓이 된다 |
| 토익 | 호출 A(표현집 판독, temperature 0) 프롬프트 — 원문 전사 | 사진에 있는 것만 옮긴다. 다듬으면 교재에 없는 표현·뜻이 초안에 섞인다 |
| 토익 | zod 가드 — `exampleSpan` ⊂ 예문, index 집합, `chunks` 조인 = 지문, `said` ⊂ 전사문(단어열·순서) | 모델이 교재·전사문 밖을 지어내는 경로를 막는다. 재요청이 잦으면 가드를 풀지 말고 프롬프트 예시를 늘린다 |
| 토익 | 전사에 기대 문장을 넣지 않음(관문 T), Q1–2는 AI가 채점하지 않음(`alignReadAloud`) | 전사가 모범답변 쪽으로 끌려가 점수가 부풀거나, 발음·억양을 모르는 LLM이 점수를 지어낸다 |
| 토익 | 교재 저작권 — 기출·ETS 샘플 금지, 교재 원문을 프롬프트·픽스처·리포트에 넣지 않음 | 저장소가 PUBLIC이다. 예시는 지어낸 영어로 쓴다 |

특히 수학에서 **`held`를 줄이려고 검산을 느슨하게 만드는 방향을 경계하라.** 이 조정이 필요해 보이면 math-verifier와 합의하고, 그 완화가 어떤 틀린 답을 통과시키는지 먼저 따진다.

## eval 실행 — 비용이 과목마다 다르다

| 과목 | 명령 | 실호출 |
|---|---|---|
| 영어 | `npm run eval:english` | 기본 카드 3회(Wolves·Pooh·Pooh+장면 메모), `EVAL_SKIP_PAGES=1`이면 2회. 게이트는 하나만 돌고 끝난다 — `EVAL_TRANSCRIPT=1`·`EVAL_CHAPTERS=1`·`EVAL_VOCAB=1`·`EVAL_WORDMEANING=1` 각 1회. 호출 H는 eval에 실호출 구간이 없다(오케스트레이터 별도 프로브) |
| 수학 | `npm run eval:math` | 픽스처 4문제 × 2~4회 = 8~16회 + 2단 픽스처 호출 E 1~2회. `EVAL_ONLY=id`면 픽스처당 2~4회, `EVAL_SKIP_2DAN=1`이면 6~12회 |
| 일본어 | `npm run eval:japanese` | **0회.** `EVAL_JAPANESE=1` 게이트는 자리만 있고 안내 문구만 찍는다(`scripts/eval-japanese.ts`의 `main`) |
| 토익 | `npm run eval:toeic` | 기본 오프라인 0회. `EVAL_TOEIC=1`이면 B 1(지어낸 표현 7개) + C 1(`EVAL_TOEIC_PART`, 기본 `opinion`) + D 1(Q11 픽스처 전사문) = 3회, `EVAL_TOEIC_PHOTO=<사진 경로>`를 주면 A 1회 더. 관문 P(사진)·T(전사)는 게이트에 없다 |

재요청이 나면 호출마다 +1회다. 모든 과목이 `EVAL_OFFLINE_ONLY=1`에서 실호출 0회이고, 이 게이트는 `globalThis.fetch`를 막는 2차 방어선까지 건다.

- `OPENAI_API_KEY`가 없으면 실호출 구간을 **실행하지 말고** 오프라인 검증만 한 뒤 "실호출 미실행"을 리포트에 명시한다.
- **비용 승인 없이 반복 실행하지 않는다.** 오프라인으로 확인할 수 있는 것은 전부 오프라인에서 끝내고 실호출은 마지막에 1회.
- 무비용 검증이 더 필요하면 루프백 스텁(`OPENAI_BASE_URL`을 로컬 서버로 고정)을 쓴다.

## eval이 못 잡는 것

**배치 병렬 호출 간의 표기 불일치**처럼 스텁으로는 절대 드러나지 않는 결함이 있다(스텁은 늘 같은 응답을 준다). 영어에서 본문 사진 15장을 6장씩 나눠 병렬 호출했더니 배치 1은 `Superman`, 배치 2는 `슈퍼맨`으로 갈렸다. **배치가 서로를 모른다면 규칙이 응답 내용에 의존하지 않고 결정적이어야 한다** — 프롬프트에 표기 규칙을 못 박는 식으로 해결한다. 일본어도 레벨별 병렬 호출·스크린샷 배치 호출이라 같은 함정이 있다. 토익도 판독(사진별)·발화 포인트(7개 묶음별)·모의고사(파트별)가 서로를 모르는 병렬 호출이다.

의미 판단도 코드로 못 잡는다 — 일본어 단어가 정말 그 JLPT 등급인지, 해설의 고칠 점이 실제 오류를 짚는지, 영어 유의어가 받은 뜻에 맞는지, 토익 모범답변이 그 등급 수준인지, 피드백 점수가 ETS 기준과 맞는지. 실물 산출물을 사람이 읽어야만 보이는 결함이 있다는 것을 리포트에 정직하게 남겨라.

## 작업 규칙

- 스키마 구조 변경(필드 추가/삭제)은 튜닝이 아니다. ai-engineer 또는 math-verifier로 반환한다.
- 픽스처 값은 스펙 원본이다. 임의로 바꾸지 말고, 바꿔야 할 근거가 있으면 리포트에 남긴다.
- git commit·push는 사용자 승인 후 오케스트레이터가 한다. main 푸시는 곧 프로덕션 배포다.

## 실호출을 금지받았다면 — 지시가 아니라 명령으로 막아라

`.env`에 실제 `OPENAI_API_KEY`가 있다. **"실호출 금지"라고 들어도 로컬 서버를 그냥 띄우면 실호출이 난다.**
2026-08-17 하루에 두 번 이 사고가 났다(에이전트가 dev/prod 서버를 띄우다 각각 3회·4회). 화면을 렌더만 해도 `prefetchSpeech()`가 `/api/tts` 합성을 보낸다.

**모든 로컬 실행 명령 앞에 키와 GCP 신호를 비워라:**

```bash
OPENAI_API_KEY= STORE_BACKEND=file GOOGLE_APPLICATION_CREDENTIALS= GOOGLE_CLOUD_PROJECT= EVAL_OFFLINE_ONLY=1 npx tsx scripts/eval-english.ts
OPENAI_API_KEY= STORE_BACKEND=file GOOGLE_APPLICATION_CREDENTIALS= GOOGLE_CLOUD_PROJECT= npm run dev
```

키가 비면 AI 라우트와 `/api/tts`가 501로 명시적으로 거절하므로 **실호출이 구조적으로 불가능**해진다. `STORE_BACKEND=file`을 명시하면 스토어 자동 감지가 꺼지고, GCP 자격증명 신호까지 비우면 설정이 어긋나도 프로덕션 Firestore를 잡을 단서가 없다(CLAUDE.md 서문).
AI 응답 자체가 필요하면 루프백 스텁을 쓴다:

```bash
OPENAI_BASE_URL=http://127.0.0.1:<포트> STORE_BACKEND=file npx tsx <스크립트>
```

**"키 없는 드라이런"을 눈으로 확인했다고 믿지 마라** — `.env`가 자동 로드돼 조용히 실호출이 난 전례가 있다.
게이트(`EVAL_OFFLINE_ONLY=1` 등)를 쓸 때는 **그 게이트가 네트워크 호출부보다 앞서 return하는지 코드로 먼저 확인**하라.
