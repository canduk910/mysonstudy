# Prompt Eval — 프롬프트 튜닝과 회귀 평가 (과목 공통)

프롬프트도 코드처럼 다룬다: **수정 → eval → 통과 → 커밋.** 아이(은우)의 반응이 유일한 진짜 지표이고, eval은 회귀를 막는 안전망이다.

## 어느 references를 읽을 것인가

작업 과목의 파일 **하나만** 읽는다. 둘 다 읽으면 컨텍스트만 늘고 다이얼 이름이 섞인다.

| 과목 | references | 다이얼 예 |
|---|---|---|
| 영어 (북카드) | `references/english-dials.md` | 단어 개수, challenge 비율, 질문 유형, hintKo 밀도, 줄거리 분량 |
| 수학 (수학코치) | `references/math-dials.md` | 비유 종류, act2 단계 수, 규칙 카드 개수, 연습문제 숫자 범위 |

## 튜닝 루프

1. 피드백 원문을 다이얼로 번역한다 — "너무 어려워"는 다이얼이 아니다. 어느 숫자를 어느 방향으로 얼마나 움직일지로 옮긴다.
2. 다이얼과 물린 **모든 지점을 한 번에** 바꾼다(아래 4중 정의).
3. `npm run eval:{subject}` 실행 → 항목별 pass/fail 표 확인 → exit 0이어야 통과.
4. 통과했을 때만 커밋을 권고한다.

## 4중 정의 — 이 프로젝트의 핵심 제약

같은 값이 **프롬프트 ↔ JSON Schema ↔ zod ↔ eval** 네 곳에 각각 있다. 한 곳만 고치면 런타임 검증과 eval이 어긋나고, 그 어긋남은 실호출을 해야 드러난다(비싸다).

두 가지를 지켜라:

- **JSON Schema에 `minLength`/`maxLength`/`minItems`를 넣지 마라.** strict 모드 제약이다. 길이·개수 검증은 zod가 담당한다.
- **숫자는 가능하면 프롬프트에 박지 말고 계산해 주입하라.** 프롬프트와 eval이 같은 함수를 부르면 4중 정의가 3중으로 줄고, 사람이 손으로 맞추던 드리프트가 사라진다. 영어의 줄거리 분량이 이 방식으로 바뀌었다 — `buildCardUserMessage`가 장면 수로 구간을 계산해 주입하고, eval이 같은 함수를 호출해 검사한다.

## 다이얼이 틀렸을 때를 알아채라

같은 항목이 2회 연속 실패하면 프롬프트를 더 조이지 마라. **근거보다 많은 것을 요구하는 다이얼은 모델이 아니라 다이얼이 틀린 것**이다.

실제 사례: 영어에서 "본문 근거가 있으면 줄거리 6~8문장"이라는 평평한 규칙을 걸었더니 모델이 5문장을 냈다. 파보니 픽스처의 장면 근거가 4개뿐이라, 근거보다 많이 쓰라는 요구였다. 모델이 규칙(지어내지 말 것)을 지킨 것이었고, 고칠 곳은 모델이 아니라 다이얼이었다 — 분량을 근거 양에 비례시키자 통과했다.

이런 판단이 서면 실패 사례와 분석을 리포트에 담아 **사용자 논의로 올린다.**

## 정확성 파이프라인은 다이얼이 아니다

건드리지 않는다:

- 영어: 표지 판독(호출 A) 프롬프트
- 수학: 검산(호출 C), `verifyScene` 규칙, `held` 판정 기준

특히 수학에서 **`held`를 줄이려고 검산을 느슨하게 만드는 방향을 경계하라.** 보류가 줄어드는 대신 틀린 답이 아이에게 전달된다. 이 조정이 필요해 보이면 math-verifier와 합의하고, 그 완화가 어떤 틀린 답을 통과시키는지 먼저 따진다.

## eval 실행 — 비용이 든다

실제 OpenAI 호출이 발생한다. 영어 3회, 수학은 문제당 2~4회다.

- `OPENAI_API_KEY`가 없으면 **실행하지 말고** 정적 검증(동기화 지점 대조)만 한 뒤 "eval 미실행"을 리포트에 명시한다.
- **비용 승인 없이 반복 실행하지 않는다.** 오프라인 케이스로 최대한 확인한 뒤 실호출은 마지막에 1회.
- 무비용 검증이 필요하면 루프백 스텁(`OPENAI_BASE_URL`을 로컬 서버로 고정)을 쓴다.

## eval이 못 잡는 것

**배치 병렬 호출 간의 표기 불일치**처럼 스텁으로는 절대 드러나지 않는 결함이 있다(스텁은 늘 같은 응답을 준다). 영어에서 본문 사진 15장을 6장씩 나눠 병렬 호출했더니 배치 1은 `Superman`, 배치 2는 `슈퍼맨`으로 갈렸다. **배치가 서로를 모른다면 규칙이 응답 내용에 의존하지 않고 결정적이어야 한다** — 프롬프트에 표기 규칙을 못 박는 식으로 해결한다.

실물 산출물을 사람이 읽어야만 보이는 결함이 있다는 것을 리포트에 정직하게 남겨라.

## 작업 규칙

- 로컬 실행 시 `STORE_BACKEND=file`을 명시한다 — 이 저장소는 로컬 실행이 프로덕션 Firestore를 향할 수 있다(CLAUDE.md 서문).
- 스키마 구조 변경(필드 추가/삭제)은 튜닝이 아니다. ai-engineer 또는 math-verifier로 반환한다.
- 픽스처 값은 스펙 원본이다. 임의로 바꾸지 말고, 바꿔야 할 근거가 있으면 리포트에 남긴다.
- git commit·push는 사용자 승인 후 오케스트레이터가 한다.

## 리포트

`_workspace/tune_report_{subject}_{n}.md` — 피드백 → 다이얼 해석 / 변경 파일·값(before→after) / 4중 정의 동기화 표 / eval 결과 표 / 커밋 권고 여부.

## 실호출을 금지받았다면 — 지시가 아니라 명령으로 막아라

`.env`에 실제 `OPENAI_API_KEY`가 있다. **"실호출 금지"라고 들어도 로컬 서버를 그냥 띄우면 실호출이 난다.**
2026-08-17 하루에 두 번 이 사고가 났다(에이전트가 dev/prod 서버를 띄우다 각각 3회·4회).

**모든 로컬 실행 명령 앞에 키를 비워라:**

```bash
OPENAI_API_KEY= STORE_BACKEND=file npm run dev
OPENAI_API_KEY= STORE_BACKEND=file npx tsx scripts/....ts
OPENAI_API_KEY= STORE_BACKEND=file npm start
```

키가 비면 라우트가 501로 명시적으로 거절하므로 **실호출이 구조적으로 불가능**해진다.
AI 응답 자체가 필요하면 루프백 스텁을 쓴다:

```bash
OPENAI_BASE_URL=http://127.0.0.1:<포트> STORE_BACKEND=file npx tsx <스크립트>
```

**"키 없는 드라이런"을 눈으로 확인했다고 믿지 마라** — `.env`가 자동 로드돼 조용히 실호출이 난 전례가 있다.
게이트(`EVAL_OFFLINE_ONLY=1` 등)를 쓸 때는 **그 게이트가 네트워크 호출부보다 앞서 return하는지 코드로 먼저 확인**하라.
